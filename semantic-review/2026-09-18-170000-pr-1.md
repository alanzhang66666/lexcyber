# Account-scoped import staging and retained raw packages

Task #1 adds the four-table import staging model plus Java storage/repository services that write a raw package to MinIO before creating its database batch, retain successful uploads, and verify size/SHA-256 on reads. The API/state-machine boundary remains closed: no controller references the new import components, while the Spring stereotypes and existing `ObjectStorage` bean provide the intended internal wiring. The main gaps are at the cross-system commit boundary and in database-level ownership integrity; both can leave behavior outside the stated task contract even though the repository queries themselves filter by owner. **Watch for:** **[confirmed, high]** a transaction commit failure can bypass MinIO cleanup; **[confirmed, high]** SQL permits cross-owner relationships; **[confirmed, high]** mapping upsert can silently remap an external identity.

**Verdict**: NEEDS_CHANGES

## High-level view

The raw package is persisted before batch SQL, but Spring commits only after `createUploadedBatch` returns through the transactional proxy. Cleanup in the method body therefore covers statement-time exceptions, not commit-time failures, and cleanup failures have no durable retry path.

Owner filtering is consistently present in the current repository queries, including case/document checks during mapping creation. The schema does not encode the same invariant across batches, items, mappings, cases, and documents, so future task #2 writes or direct maintenance SQL can create cross-account links that all four staging tables were meant to prevent.

External-resource identity is unique per owner/producer/dataset/type/id, but conflict handling overwrites the existing internal target. That turns repeated imports into an implicit remapping operation instead of detecting identity drift.

The JSON fields are modeled as Java maps but SQL accepts any JSON shape, while create records reject otherwise-valid maps containing JSON nulls. Raw package operations also multiply whole-package byte arrays and keep database transactions open across object-store reads; these costs become material when task #2 exposes ingestion.

No task #1 tests exercise migration constraints, MinIO compensation, retained-object integrity, corruption detection, or owner isolation. Static wiring inspection found the required Spring beans, but the available Docker/Maven validation did not complete in this environment.

1. **[High, confirmed] Commit-time MinIO orphan** — Spring commits after the compensation `try/catch` has returned, and failed deletes are only logged. Put commit inside the compensated boundary and add durable orphan cleanup/retry.

3. **[High, confirmed] External mapping remap** — `ON CONFLICT` replaces the established internal case/document target. Reject target drift or update only revision/source fields when the internal identity is unchanged.

<details><summary>Details</summary>

## MinIO compensation misses the actual database commit boundary

**[confirmed, high]** `ImportService.createUploadedBatch` is transactional, writes MinIO at lines 32-38, and catches database-path exceptions at lines 39-50. Spring's transaction interceptor performs the commit after the method returns, so a commit failure cannot enter this catch and leaves an unreferenced raw package. Even for exceptions caught in the body, a failed delete is only logged, leaving no durable cleanup record for a package that may contain sensitive case material. Move the database unit into a `TransactionTemplate` (so commit completes inside the surrounding `try`) or register commit-aware synchronization, and add a retryable orphan-cleanup mechanism for failed MinIO deletes.

## Database ownership is filtered by Java but not enforced relationally

**[confirmed, high]** `V11__import_staging.sql` gives the batch an owner at line 3, but `import_items.case_id` is an independent FK at line 51 and can reference a case owned by another account. `external_resource_map` independently references an owner, batch/item, case, and document at lines 99-122 without any composite owner constraint, so SQL can accept owner A paired with owner B's batch or case. The current insert/upsert queries guard these joins (`ImportStore.java:95-106, 168-172`), but that is not the account-owner-scoped four-table invariant and is fragile once task #2 adds transition/update paths. Encode owner consistency with composite candidate keys/FKs (or equivalent triggers), including batch-to-item, batch-to-case, mapping-to-batch, mapping-to-case, and document-to-case relationships.

## External identity conflicts silently rebind internal resources

**[confirmed, high]** `ImportStore.upsertMapping` resolves a conflict on the external identity at lines 172-174, then replaces `batch_id`, `item_id`, internal type/id, `case_id`, and `document_id` at lines 175-181. A later package can therefore move an established external resource from one internal case/document to another under the same account, while callers receive the row as a successful upsert. Preserve the original internal identity and update only revision/source metadata, or make the conflict update conditional on identical targets and return an explicit conflict when remapping is attempted.

## JSONB columns and Java Map contracts accept different data

**[confirmed, medium]** Metadata/error/input/output/diff columns in `V11__import_staging.sql:19-20, 52-54, 81-82, 115` have no `jsonb_typeof(...)= 'object'` checks, but `ImportStore.readMap` at lines 319-329 deserializes them specifically as `Map`. A scalar or array accepted by PostgreSQL will make row mapping fail at runtime. In the other direction, all create records use `Map.copyOf` (`ImportBatchCreate.java:13`, `ImportItemCreate.java:17`, `ImportStepCreate.java:15`, `ExternalResourceMappingCreate.java:24`), which throws on a null value even though `{ "field": null }` is valid JSON. Add object-shape checks for map-backed JSONB columns and copy metadata through a JSON-compatible deep-copy/validation path that preserves JSON nulls.

## Whole-package copies amplify heap use and object-store latency holds DB transactions

**[confirmed, medium]** A package is cloned in the batch record constructor and accessor (`ImportBatchCreate.java:12,18`) and again by `requireRawPackage` (`ImportPolicies.java:15-22`) before `RawPackageStorage` sends the snapshot at lines 17-24. A nominal 50 MiB upload therefore has at least three live server-side copies during the write, with sensitive bytes left for GC after success. The read path is also marked read-only transactional (`ImportService.java:75`) while it downloads the full object and hashes it at lines 79-87, retaining a database connection across MinIO I/O. Reduce defensive copies to one bounded buffer (or stream while hashing), clear temporary buffers where ownership permits, and end the database lookup transaction before object-store I/O; enforce a bounded read before allocating the returned object.

## Critical cross-store and integrity behavior has no regression coverage

**[confirmed, medium]** No Java test under `server/src/test` references `ImportService`, `ImportStore`, `RawPackageStorage`, `import_batches`, or `external_resource_map`. The missing coverage includes commit-time failure cleanup, delete-failure recovery, successful raw retention, hash/size mismatch rejection, owner-scoped reads/writes, nullable step items, FK/CHECK behavior, and remap conflicts. Add focused service tests with a controllable transaction/storage double plus PostgreSQL integration tests for V11 before task #1 ships.

Validation was limited: the Docker Maven build remained in dependency resolution and the execution environment terminated the command before producing a compile/test result.
