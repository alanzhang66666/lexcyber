# 三案协作导入的服务端幂等闭环复审

本轮限定检查协作数据 Schema、三案 manifest、导入器、案件/复核接口及 Flyway V10。上轮 10 项中，案件/复核 POST 崩溃窗口、材料 TOCTOU、导入引用 gate、stale module、崩溃锁、日期格式、路径越界、账号规范化和报告路径暴露均已修复；逐项报告的普通网络与响应异常也已覆盖，但 checkpoint IO 故障仍可绕过报告。服务端以事务内幂等占位行和 `FOR UPDATE` 串行并发重放，V10 外键类型及 importer 的 201 响应预期一致。**Watch for:** **confirmed** checkpoint 写入故障会在异常处理器中再次失败而不生成报告；**confirmed** 案件请求 hash 对 JSON 对象键序敏感；**confirmed** 新增案件/复核幂等没有并发、冲突或回滚集成测试。

**Verdict**: NEEDS_CHANGES

## High-level view

案件创建按账号与幂等键占位，复核开单按账号、案件与幂等键占位；同一事务持有幂等行锁直至资源 ID 回填，因此同键并发会等待并重放同一资源，失败事务也会连同占位行回滚。控制器对首次创建和重放都返回 201，契约与 importer 的调用约定一致。

V10 的外键目标和类型与既有账号、案件、复核表一致，Compose 也会从现役 `db/migration/app` 链加载它；但没有测试执行迁移后的案件/复核并发与回滚场景，关键保证只由代码审阅确认。

案件 metadata 的 hash 没有稳定排序，语义相同但键序不同的 JSON 会被当作冲突；checkpoint 保存失败后，异常分支再次保存同一路径，导致审计报告无法落盘。

1. **Medium · checkpoint IO 仍可绕过报告（confirmed）** — 异常处理器再次写同一 checkpoint，第二次失败会在记录 blocked 项和写报告前退出；将 checkpoint 恢复写改为 best-effort，并在外层 `finally` 生成报告。
2. **Medium · CaseCreate hash 对 JSON 键序敏感（confirmed）** — 语义相同的 metadata 可因对象键序不同返回 409；使用递归稳定排序的 canonical JSON 计算请求 hash。
3. **Medium · 服务端幂等缺少并发/回滚测试（confirmed）** — 新案件与复核幂等没有覆盖同键并发、内容冲突、事务回滚和重放响应；增加真实 PostgreSQL 集成测试后再交付。

## Checkpoint IO 故障仍可跳过逐案报告

逐案主体现在用 `except Exception` 捕获传输、响应解码和普通 IO 异常，解决了上轮大部分无报告路径。不过，`import_case` 内任一次 `save_checkpoint` 抛出 `OSError` 后，异常处理器会先设置 blocked 状态，再无保护地调用同一个 `save_checkpoint`；第二次失败直接越出循环，`imported.append` 和循环后的 `write_report` 都不会执行（`scripts/import_three_case_demo.py:1051-1083`）。这是 **confirmed** 的残留审计缺口，磁盘满、权限变化或原子替换失败恰好会同时失去 checkpoint 与本次运行报告。

应让异常分支的 checkpoint 持久化成为 best-effort，并在外层 `finally` 基于内存中的逐案状态尝试写报告；报告写入失败也应至少向 stderr 输出完整摘要和非零退出码。

## CaseCreate hash 把 JSON 键序当成请求内容

`caseRequestHash` 构造顶层 `LinkedHashMap`，但直接用应用 `ObjectMapper` 序列化嵌套 metadata；该 mapper 没有启用 map key 排序（`server/src/main/java/com/lexcyber/server/domain/CaseService.java:193-204`）。因此 `{"a":1,"b":2}` 与 `{"b":2,"a":1}` 会产生不同 hash，尽管 JSON 对象语义、最终 PostgreSQL `jsonb` 和 CaseView 内容相同；复用同一幂等键会得到 409。这是 **confirmed** 的假冲突，与契约所说的“不同请求内容”不一致，也使通过不同 JSON serializer 重试不稳定。

应使用启用 `SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS` 的专用 canonical mapper，或先转为递归排序的 JsonNode 后计算 hash。

## 并发重放和事务回滚没有服务端回归测试

新增代码的并发策略依赖 PostgreSQL `INSERT ... ON CONFLICT DO NOTHING` 等待、随后 `SELECT ... FOR UPDATE` 读取已提交绑定，以及 Spring 事务把空占位与资源创建一起回滚。现有测试只覆盖材料上传幂等；搜索不到案件创建或复核开单的同键重放、不同内容 409、跨账号/跨案件作用域、并发双请求、资源创建失败回滚后重试，以及控制器重放仍返回 201 的测试。这是 **confirmed** 的中风险覆盖缺口，尤其无法自动证明 V10 FK 和锁序在真实 PostgreSQL 上工作。

应增加基于现有 PostgreSQL/Testcontainers 测试基座的集成测试，用两个独立事务并发调用相同键，并注入一次资源创建失败后验证幂等占位回滚；同时覆盖 hash 冲突和 API 响应。
