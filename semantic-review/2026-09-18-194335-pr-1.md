# Recoverable case-package import state machine

The change adds the authenticated upload → validate/diff → approve → apply → retry flow, with Engine-side package normalization and Java-side staged projection into cases, documents, event bindings, draft facts, draft compliance/conviction modules, and a conviction review. CAS predicates protect ordinary concurrent API calls, and the owner-scoped query/FK graph from the previous pass remains intact. The durable-step design does not survive an interrupted apply, however, and its retry path re-executes steps already recorded as complete. **Watch for:** **[blocker, confirmed]** batches can be permanently stranded in `applying` with `running` steps; **[high, confirmed]** completed steps are replayed; **[high, confirmed]** a stale create diff can reuse a later case mapping without checking the payload hash; **[high, confirmed]** apply materializes as much as 512 MiB of uncompressed ZIP content in heap, plus copies; **[medium, confirmed]** terminal/active timestamps violate the API's state semantics; **[medium, confirmed]** raw internal exception messages are returned in public DTOs; **[medium, confirmed]** all validation persistence integrity failures are mislabeled as release conflicts; **[low, confirmed]** the Java state machine has no focused tests.

**Verdict**: NEEDS_CHANGES

## High-level view

Validation verifies the retained object's raw hash, enforces package/file descriptors and media checks, and persists a normalized plan. The create/no_op/conflict decision is owner-scoped and compares the case payload plus every document hash, but that decision is not revalidated when apply encounters a mapping created after validation.

Apply is split into durable-looking case, document, event, facts, module, and review steps. The records are checkpoints only in name: no recovery entry accepts `applying`, no stale-running lease exists, and completed outputs are stored but never consumed, so retry starts the action chain again.

The projection keeps facts and modules in draft and opens a human conviction review; the only task creation on this path is the existing automatic `document.parse` task from document upload. It does not call sentencing, compliance-analyze, or conviction-analyze task creation.

The public DTO omits the object-store key and normalized plan, but exposes persisted error maps. Those maps are built from arbitrary exception messages, including PostgreSQL and unexpected Engine package-reader failures.

The ZIP checks bound entry count and size, but apply expands the entire validated archive into a Java map with a 512 MiB ceiling. That is an availability boundary rather than a streaming bound.

1. **[Blocker, confirmed] Interrupted apply is unrecoverable** — batches/items left `applying` with a `running` step cannot enter either apply or retry; add stale-claim leasing and an atomic recovery transition.
2. **[High, confirmed] Completed steps are replayed** — `runStep` executes completed actions and ignores persisted outputs; resume from checkpoint outputs or explicitly reconstruct state without replaying completed mutations.
3. **[High, confirmed] Stale create diff bypasses payload conflict** — `ensureCase` reuses a mapping created after validation without comparing its source hash; recheck `payloadSha256` at apply time and fail closed.

5. **[Medium, confirmed] State timestamps are inconsistent** — active retries retain `completedAt`, terminal items never receive it, and batch/item `startedAt` is never set; update timestamps in CAS statements and strengthen V11 CHECKs.
6. **[Medium, confirmed] Public errors leak internal messages** — raw Java, PostgreSQL, and unexpected Engine exception text is persisted and returned; log details internally and expose stable sanitized errors.
7. **[Medium, confirmed] Integrity failures are misclassified** — every validation `DataIntegrityViolationException` becomes duplicate-release 409; identify that unique constraint specifically and treat other failures as internal persistence errors.
8. **[Low, confirmed] Java Import behavior is untested** — add PostgreSQL-backed orchestration tests covering CAS races, crash recovery, checkpoint resume, partial retry, mapping races, owner isolation, timestamps, and analyzer non-creation.

<details><summary>Details</summary>

## Interrupted apply has no legal recovery transition

**[blocker, confirmed]** `apply` first moves the batch from `approved` to `applying` (`ImportService.java:206-216`), then moves each item to `applying` and claims a step as `running` in separate transactions (`ImportService.java:351-378`; `ImportStore.java:439-446`). Runtime exceptions inside the request are converted to failed step/item/batch states, but process termination, container restart, or loss after a committed claim bypasses those handlers. A subsequent `apply` accepts only `approved` (`ImportService.java:209-212`), while `retry` accepts only `failed` or `partially_completed` (`ImportService.java:261-269`); `resetFailedSteps` also ignores `running` (`ImportStore.java:485-495`). The batch and item therefore remain permanently `applying` and the advertised recoverable-step index in V11 has no consumer. Add a lease/heartbeat or stale-claim recovery transition that atomically reclaims `applying` batches/items and `running` steps.

## Completed checkpoints are executed again instead of resumed

**[high, confirmed]** `runStep` skips `claimStep` when a row is `completed`, but unconditionally calls `action.get()` afterward (`ImportService.java:489-500`). Although outputs such as `caseId`, `documentIds`, and `reviewId` are written to `output_json`, no production path reads them (`ImportService.java:357-377`; `ImportStore.java:456-463`). A retry after `modules.write` fails will rerun completed case/document/event/facts actions; if a user changes facts before retry, the replayed completed `facts.write` now fails with `IMPORT_FACTS_CONFLICT`, so the original failed module step is never reached. Resume from validated checkpoint outputs, or make explicit reconstruction/read-only verification separate from replaying completed actions.

## Stale create diffs can bypass the content-change conflict rule

**[high, confirmed]** validation labels an item `create` only when no case mapping exists and labels a differing mapped payload `conflict` (`ImportService.java:305-326`). Between validation and apply, another approved batch can create the same `(owner, producer, dataset, externalCaseId)` mapping. `ensureCase` then returns that mapped case without comparing `item.payloadSha256()` to `mapping.sourceSha256()` (`ImportService.java:381-386`), unlike `ensureDocuments`, which rejects a changed document hash (`ImportService.java:402-409`). If the later payload differs only in case title or metadata while downstream documents/facts/modules happen to match, the stale item reaches `applied` instead of conflict. Recheck the case mapping hash at apply time and fail closed before any downstream mutation.

## Whole-archive expansion makes one apply a heap-exhaustion candidate

**[high, confirmed]** upload accepts a 50 MiB ZIP, while the validated transport allows up to 512 MiB uncompressed. Apply downloads the raw package as one byte array and passes it to `ImportArchiveReader` (`ImportService.java:219-220, 280-288`); the reader retains every uncompressed entry in `Map<String, byte[]>` up to `MAX_TOTAL_BYTES` (`ImportArchiveReader.java:23-28,60-107`), and `require` clones each document again (`ImportArchiveReader.java:38-57`). `ByteArrayOutputStream.toByteArray()` also creates a second entry array during expansion. A single valid high-ratio package, or several concurrent applies, can therefore exceed a typical Java heap despite respecting every package limit. Stream validated entries from object storage/ZIP to document storage with cumulative limits, or lower/enforce a server-heap-aware package budget and concurrency cap.

## Batch and item timestamps do not represent their states

**[medium, confirmed]** batch CAS updates only `status` and `updated_at`, so entering validation/apply never sets `started_at` (`ImportStore.java:252-258`). Retry transitions a terminal batch back through `approved` and `applying` without clearing its prior `completed_at`, while `finishBatch` later writes it again (`ImportStore.java:306-316`). Item transitions never set either `started_at` or `completed_at`, including `no_op` and `applied` (`ImportStore.java:365-397`; `ImportService.java:314-326,377-379`). V11 only requires `completed_at` for a completed batch and a `case_id` for an applied item (`V11__import_staging.sql:30-34,64-73`), so active batches can appear completed and terminal items can have no completion time in the public contract. Update timestamps in each state CAS and add CHECK constraints covering terminal versus active states.

## Public error maps expose internal exception text

**[medium, confirmed]** every stored batch/item/step failure uses `Throwable.getMessage()` (`ImportService.java:559-561`), and all three response DTOs return those error maps directly (`ImportBatchResponse.java:20,32`; `ImportItemResponse.java:18,28`; `ImportStepResponse.java:10,16`). Validation persistence can therefore reveal PostgreSQL constraint/SQL details, while Engine's broad package-reader fallback returns `str(exc)` (`engine/api.py:104-114`) and Java embeds that message in the public batch. Keep detailed diagnostics in server logs/audit with a correlation ID and expose only stable error codes plus curated package-validation messages.

## Integrity failures are all reported as duplicate releases

**[medium, confirmed]** the `DataIntegrityViolationException` catch around all of `persistValidation` converts any DB integrity failure into HTTP 409 `IMPORT_RELEASE_CONFLICT` (`ImportService.java:171-178`). That transaction also deletes/recreates items and writes plan fields, so CHECK, FK, length, or malformed Engine-response failures unrelated to the release uniqueness index receive the same user-facing diagnosis and are retried as if another release exists. Detect the named release constraint specifically; treat other integrity failures as sanitized internal persistence errors, and validate the Engine response before opening the staging transaction.

## State-machine regressions have no Java coverage

**[low, confirmed]** no test under `server/src/test` references `ImportService`, `ImportController`, `ImportArchiveReader`, `ImportPlanProjector`, `import_batches`, or `external_resource_map`. Add PostgreSQL-backed service tests for concurrent validate/approve/apply CAS, crash reclamation, completed-step resume, stale mapping races, partial failure/retry, no_op hashing, owner isolation, error sanitization, timestamp CHECKs, and analyzer non-creation. Python package tests exist, but they do not exercise the Java orchestration.
