# Lease-fenced import recovery and bounded archive extraction

The scoped import path recovers expired work without discarding completed checkpoints. A step action now executes while the active batch lease row is locked, so recovery cannot grant a replacement worker an overlapping action window. External-resource mappings retain the first payload source claim, and ZIP extraction holds one exact-size entry buffer alongside the raw package. **Watch for:** no real blocker or high-severity concern remains in the requested recovery, stale-action replay, checkpoint reuse, payload-claim, or memory-duplication paths.

**Verdict**: APPROVED

## High-level view

Expired recovery returns only in-flight items and steps to runnable states, while subsequent applies use retained completed-step outputs. The action, completion, and lease renewal occur under the batch lease row lock; the recovery transition cannot run until that transaction completes. A conflicting payload source cannot update an existing external mapping, and entry extraction avoids the former growable-buffer plus copy peak.

<details><summary>Details</summary>

`recoverExpiredApply` resets `applying` items and `running` steps only after the batch lease deadline, retaining completed records and outputs. `runStep` reads a completed output before a new claim; otherwise its transaction obtains `lockApplyLease`, performs the domain action, completes the step, and renews the lease. This prevents the former sequence in which recovery could replace an expired worker and the original worker could then execute its action.

`ensureCase` rejects an existing external-case mapping whose payload hash differs, while the mapping conflict update also requires its source hash/version and internal target to remain unchanged. `ImportArchiveReader.readEntry` creates one array of the validated expected entry size and fills it directly, rather than retaining a `ByteArrayOutputStream` buffer plus a copied result.
