# 可恢复的三案协作导入与冻结 Schema

本次改造为三案导入增加固定账号、协作身份、服务端对账、checkpoint 和逐项报告。上传使用服务端 Idempotency-Key，事件、facts、modules 和 review 也在写入前读取当前状态。阻塞交付的缺口集中在非幂等 POST 的崩溃窗口、材料预检与实际上传之间的时间窗口，以及未覆盖实际导入约束的 schema/引用 gate。**Watch for:** **likely** 案件创建和复核开单在请求进行中崩溃时仍可能重复；**confirmed** 已通过 hash 的材料可在上传前被替换；**confirmed** confirmed+factsStale 模块仍被当作成功并继续开复核。

**Verdict**: NEEDS_CHANGES

## High-level view

checkpoint 在各阶段前后原子替换，恢复时通过服务端身份或内容对比重新确认状态。上传 POST 有服务端内容绑定的幂等键；案件创建和复核开单没有等价约束，POST 前后的扫描无法封闭“旧请求仍在服务端执行、恢复扫描尚未看到结果”的窗口。

数据集和材料在认证及业务写入前预检，但预检只保存路径和当时的 hash，上传时重新读取文件。archive_entry 还能越出 docs-dir；引用 gate 也没有证明证据文档属于实际会上传的 case_material，或材料格式受公开上传接口支持。

facts/module GET 字段与当前 Java DTO 对齐，更新也携带服务端 version。例外是 confirmed 且 factsStale 的 module：脚本将其计为完成，并以旧 facts 快照版本继续创建或复用复核。

checkpoint digest 能隔离交付版本，但锁无崩溃恢复协议，owner identity 又使用调用方输入的大小写敏感用户名。逐项报告只在主循环正常结束后生成，未包装的网络/IO 错误不会留下本次运行报告。

6. **Medium · 日期 format 未执行（confirmed）** — jsonschema 未启用 FormatChecker，无效 analysis_as_of_date 会穿过 preflight；启用格式检查并增加负例。
7. **Medium · archive_entry 越界读取（confirmed）** — 绝对路径或 `..` 可读取并上传 docs-dir 外文件；规范化路径并校验 resolve 后仍位于根目录内。
8. **Medium · 异常路径无逐项报告（confirmed）** — URLError/OSError/响应解码错误会绕过报告写入；在 finally 中由 checkpoint 和已完成项生成失败报告。

<details><summary>Details</summary>

## High — 非幂等案件/复核 POST 仍有崩溃重复窗口

`resolve_case` 在创建前扫描服务端，创建成功后才保存 caseId；`ensure_conviction_review` 采用同类“列表、POST、保存 reviewId”流程（`scripts/import_three_case_demo.py:451-479`, `766-801`）。进程在请求发出后被杀死时，服务端事务仍可继续；清理遗留锁后立即恢复，新的扫描可能早于旧事务提交，于是再次 POST。案件表没有 producerId+externalCaseId 唯一约束，ReviewService.open 也直接生成 UUID，因此 **likely** 产生重复案件或复核。同一运行的请求中断也存在该窗口，不只是 README 已承认的多主机竞态。

需要为案件创建和复核开单增加服务端幂等键/唯一约束；否则不能承诺崩溃窗口可恢复。上传由 Java upload_idempotency 将 key 与 request hash 绑定，不存在同类缺口。

## High — 预检 hash 与上传字节不是同一快照

`prepare_materials` 计算 SHA-256 后只保存 `Path` 和 hash（`scripts/import_three_case_demo.py:225-249`），真正上传才调用 `source.read_bytes()`（`535-544`）。其间包含认证、案件处理和任务轮询；文件被替换时，checkpoint/report 仍记录旧 hash，后续又只比较文件名、角色和当前 size（`545-551`）。这是 **confirmed** 的 TOCTOU，网络写入可携带未通过清单 SHA-256 的内容。

应从预检生成不可变快照并上传该快照，或在 POST 前重新校验实际发送字节；sourceHash 必须对应发送内容。

## High — 引用 gate 没有证明对象可由公开 API 导入

schema 只要求 evidence.document_id 是稳定 ID，语义校验也只确认它存在于 documents（`contracts/schemas/collaboration-case-bundle.schema.json:108-118`, `engine/adapters/case_bundle.py:151-156`），导入器却只上传 case_material（`scripts/import_three_case_demo.py:502-504`）。evidence/fact 指向 benchmark_annotation 或 legal_review_summary 时，dataset 会通过 preflight；建案和上传发生后，`build_t1_fact_view` 才因缺少 DocumentView.id 失败。schema 也未限制 case_material 为 PDF/DOCX，`.doc` 等格式会在建案后才被 Java 拒绝。两条路径均 **confirmed** 违反“所有引用和材料条件在业务写入前通过”。

`analyses` 仍是宽泛 object（schema `24-29`），其 facts、jurisdiction_source_ids 等 projection 引用也未完整校验。预检必须基于“可上传文档”集合检查所有后续 projection 引用和格式。

## High — confirmed stale module 仍进入成功复核

Java 的 `factsStale` 表示 module 的 facts_updated_at 不等于当前 facts 更新时间。脚本遇到 confirmed、内容相同、factsStale=true 时只记录 `confirmed_stale`，随后继续使用该 version 开复核并将整案标成 completed（`scripts/import_three_case_demo.py:700-707`, `882-912`）。这是 **confirmed** 的状态错误：复核绑定旧 facts 快照，而 confirmed 保护又禁止脚本 PUT 刷新。

该状态应阻断当前案并要求人工处理；若产品允许复核 stale 内容，至少必须降级整体状态并显式绑定 stale facts 版本。

## Medium — 硬崩溃永久遗留 checkpoint 锁

锁以 O_EXCL 创建，只在 Python `finally` 删除（`scripts/import_three_case_demo.py:367-382`）。断电或强杀不会执行 finally，之后所有恢复都无条件失败；锁里只有 PID，没有主机/启动身份、存活检查、租约或受控解锁。这是 **confirmed** 的恢复阻塞，人工删除又可能放开仍运行的导入。

应使用进程退出时由 OS 自动释放的文件锁，或实现可审计 stale-lock recovery。

## Medium — date format 只是 schema 注解

analysis_as_of_date 声明了 `format: date`（`contracts/schemas/collaboration-case-bundle.schema.json:12`），但 `_schema_issues` 构造 `Draft202012Validator(schema)` 时未传 FormatChecker（`engine/adapters/case_bundle.py:32-38`）。jsonschema 默认不执行 format，因此无效日期 **confirmed** 通过 gate；若错误在后续案件，前案已写入后 Java 才拒绝 CaseCreate。

应启用对应 draft 的 FormatChecker，并覆盖公开 API 日期负例。

## Medium — archive_entry 可越出 docs-dir

archive_entry 仅要求非空（`contracts/schemas/collaboration-case-bundle.schema.json:57`），`find_material` 直接接受 `docs_dir / archive_entry` 的存在文件（`scripts/import_three_case_demo.py:169-182`）。绝对路径绕过 docs-dir，`..` 穿越父目录；bundle 提供匹配 hash 后文件会被上传。这是 **confirmed** 的本地文件读取/外传边界缺口。

应拒绝绝对路径、父目录段和非规范路径，并验证 resolve 后路径仍在 docs-dir；上传 filename 也需 multipart-safe 处理。

## Medium — 未包装故障绕过逐项报告

逐案循环只捕获 `ImportConflict` 和 `T1ContractError`，报告在循环结束后才写（`scripts/import_three_case_demo.py:981-1022`）。URLError、OSError 和响应 JSON 解码错误会 **confirmed** 直接终止；此前案件可能已完成，当前 checkpoint 也可能已推进，却没有本次报告。

应在 finally 中基于 checkpoint 和已收集项目写报告，并将传输/IO 错误转换为 failed/blocked 条目。

## Medium — owner identity 使用输入用户名而非规范账号

服务端按 lower-case username 登录，`authenticate` 却返回环境变量原文，checkpoint target 再做完全相等比较（`scripts/import_three_case_demo.py:294-303`, `324-349`）。同一 owner 用 `Alice` 与 `alice` 登录会拿到同一账号 token，却 **confirmed** 不能复用 checkpoint；该字段也不是稳定 owner UUID。

应绑定登录响应的规范 username，最好绑定服务端 account ID。

## Low — 报告持久化本机身份和绝对路径

upload 条目保存 sourcePath，顶层保存 username、docsDir 和 checkpoint 绝对路径（`scripts/import_three_case_demo.py:570-580`, `929-955`）。`.gitignore` 的 `.t1-*` 避免默认提交，token/password 也未落盘；但报告被附到工单或复制时会 **confirmed** 暴露本机账号和目录拓扑。应默认写 archiveEntry 或脱敏路径。

新增测试只覆盖材料发现和 placeholder，**confirmed** 未覆盖 checkpoint、崩溃重放、legacy adopt、GET 对比、confirmed/stale 和报告失败路径。当前 Python 3.10 环境未安装项目声明的 jsonschema/pytest/ruff，无法执行测试与 linter；`git diff --check` 未发现 whitespace 错误。
