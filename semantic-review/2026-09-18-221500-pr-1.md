# Lease recovery and immutable import identity claims

This revision makes interrupted `applying` work reclaimable, resumes completed steps from persisted outputs, rechecks an already-present case mapping’s payload hash, and bounds archive expansion to the raw ZIP plus one requested entry. Those paths address the earlier single-worker failure modes, but the new five-minute lease is not maintained while a domain action runs and has no fencing token, so a slow live worker can be recovered and overlapped with a second worker. The case payload recheck is likewise non-atomic with first mapping insertion, allowing two concurrent stale applies to overwrite the identity’s source hash when their case projection is identical. **Watch for:** **[high, confirmed]** a still-live apply can be reclaimed and run concurrently after five minutes; **[high, confirmed]** a concurrent first mapping claim can overwrite the source payload hash and later classify unapplied content as `no_op`.

**Verdict**: NEEDS_CHANGES

## High-level view

**[high, confirmed]** The batch lease is renewed before and after steps, rather than during the potentially unbounded case, document, facts, module, or review action. Lease expiry is therefore treated as proof of worker death even when the original worker is still mutating domain state, and recovery resets its live step before a second request starts another apply.

**[high, confirmed]** The stale payload check correctly rejects a mapping that exists before `ensureCase` reads it. Two applies that both observe no mapping still converge on the same idempotent case request and the mapping upsert accepts that same internal case while replacing `source_sha256`; the external identity then records the losing payload rather than the applied one.

## A five-minute action is recovered while it is still changing state

**[high, confirmed]** `runStep` sets the batch and step lease to five minutes immediately before `action.get()` and only renews the batch after that action returns (`ImportService.java:511-520`). The actions include synchronous object-store-backed document upload and domain writes, with no heartbeat or deadline enforcement. Once five minutes elapse, another `apply` or `retry` sees the batch as `applying` and `recoverExpiredApply` changes it back to `approved`, resets every `applying` item, and turns every `running` step into `pending` (`ImportService.java:209-213, 277-280`; `ImportStore.java:329-353`). The second request can then claim and execute the same step while the original request is still inside its action.

The original request has no lease ownership token to prevent stale completion: `completeStep` and `failStep` match only `status = 'running'`, while `finishBatch` matches only `status = 'applying'` (`ImportStore.java:521-548, 318-325`). Depending on timing, the two workers can each persist domain mutations and race to record inconsistent step/item/batch outcomes. Renew the lease asynchronously for the full action duration and persist a generation token when claiming the batch/step; recovery and all terminal writes must compare that token. A fixed action timeout that reliably terminates the mutation before the lease expires is an alternative, but the current code provides neither.

## Concurrent absent-mapping checks can replace the payload identity

**[high, confirmed]** `ensureCase` rejects a mapped case whose `sourceSha256` differs from the item, but the `findMapping` check and `upsertMapping` occur in separate transactions around `cases.create` (`ImportService.java:390-411`). Two approved batches with the same external case identity can both observe no mapping. If their case title, jurisdiction, date, and metadata match, `CaseService.create` deliberately replays the same case for its stable idempotency key (`CaseService.java:42-50, 181-205`) even when the package payloads differ elsewhere, such as facts, modules, or the normalized payload digest.

The first mapping insert wins the unique key. The second `upsertMapping` then accepts the row because its internal resource and case are identical, but its conflict update replaces `source_sha256` with the second batch’s value (`ImportStore.java:192-205`). If the first batch then completes and the second fails at a later facts/modules conflict, the map says the second payload is already applied. A later validation compares only the payload hash and document mappings, so it can label the second content `no_op` without its facts/modules ever having been applied. Lock or insert the mapping as an immutable hash-bound claim before creating/replaying the case; on a unique-key conflict, read and require the existing hash to match rather than updating it.
