# Recoverable import apply with leased execution

V11 persists batch and step lease tokens, recovers expired `applying` batches, resumes ledgered steps, and rejects an external-resource mapping whose source hash differs from the first claim. The heartbeat renews both leases while a step action is active, but two high-severity gaps remain: an expired worker can execute a step body after its replacement has completed that step, and the archive reader duplicates a requested entry at its peak allocation. **Watch for:** **[high, confirmed]** completed import steps can still have their domain action replayed by a stale worker; **[high, confirmed]** a maximum ZIP entry coexists with an additional full-size buffer, breaking the raw-ZIP-plus-one-entry memory limit.

**Verdict**: NEEDS_CHANGES

## High-level view

**[high, confirmed]** Lease tokens fence state transitions but not the action itself. Recovery can replace a stopped worker and complete a step before the stopped worker resumes; that worker enters `action.get()` without a current-token check and only notices heartbeat loss after it has performed the domain operation.

**[high, confirmed]** Extracting one entry uses a dynamically growing `ByteArrayOutputStream` and `toByteArray()`. At the return boundary, the raw ZIP, the stream’s backing buffer, and its defensive result copy can all be live.

1. **[High, confirmed] Stale workers can replay completed actions** — fence the action start against the current batch/step token and prevent an expired worker from executing domain writes after recovery; completion-token checks only protect the ledger.
2. **[High, confirmed] ZIP extraction exceeds the advertised memory bound** — read into a single exactly bounded entry buffer (or stream directly into the consumer) instead of retaining `ByteArrayOutputStream`’s growth buffer and a `toByteArray()` copy alongside the raw ZIP.

<details><summary>Details</summary>

## Token-guarded bookkeeping does not fence a resumed worker’s domain action

**[high, confirmed]** `recoverExpiredApply` changes a batch back to `approved` and resets every `running` step to `pending` after the five-minute deadline (`ImportStore.java:347-371`). A replacement can then claim, run, and complete the same step with its new token (`ImportStore.java:523-558`). If the original worker was paused immediately after `claimStep`, it resumes with the old token. `runStep` starts its heartbeat and invokes `action.get()` unconditionally; `heartbeat.requireActive()` runs only after the action returns (`ImportService.java:516-528`).

The stale worker can therefore re-execute `ensureCase`, `ensureDocuments`, event binding, facts, module writes, or review opening after the replacement marked its step completed. `completeStep` prevents it from overwriting the step record, but none of those domain calls receives or verifies the import lease token. This breaks the requirement that completed steps never replay and leaves correctness dependent on separate downstream idempotency. Claim a token-bound execution fence immediately before every action and make the downstream mutation participate in it, or run the action under a database-held fence that recovery cannot supersede until the old worker cannot write.

## One requested ZIP entry is retained twice at extraction peak

**[high, confirmed]** `ImportArchiveReader` keeps the full raw ZIP in `rawZip` (`ImportArchiveReader.java:26-39`). For a requested entry, `readBounded` grows a `ByteArrayOutputStream` up to the 50 MiB entry maximum and `toByteArray()` allocates a second array for the returned content (`ImportArchiveReader.java:128-141`). Before the stream buffer becomes collectible, `readEntry` returns the defensive copy while the original raw ZIP remains resident (`ImportArchiveReader.java:89-115`).

With separately enforced 50 MiB raw-package and entry limits (`ImportPolicies.java:10-19`; `ImportArchiveReader.java:28-30`), this reaches the raw ZIP plus two full entry-sized arrays, excluding `ByteArrayOutputStream` growth over-allocation. Concurrent applies multiply the excess. Allocate one bounded array from the validated expected size and fill it directly, or change the consumer contract to stream the entry; do not copy a complete growable buffer at the reader boundary.

</details>
